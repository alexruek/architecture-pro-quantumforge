# Задание 6. Автоматическое ежедневное обновление базы знаний

Индекс FAISS из заданий 3-5 теперь обновляется без ручного вмешательства: раз в сутки скрипт находит в базе знаний новые, измененные и удаленные документы и точечно правит индекс. Бот подхватывает новую версию индекса без перезапуска.

## Источник данных

Папка knowledge_base/ (файлы .md и .txt, включая вложенные папки). Это та же база знаний, из которой индекс строился в задании 3, поэтому ключи источников в метаданных чанков (knowledge_base/01_ksarn_velgor.md и т. д.) совпадают с теми, что уже лежат в индексе.

Новый документ "подхватывается" так: файл кладется в knowledge_base/ (вручную, через git pull, синхронизацией с внешним хранилищем), при следующем запуске скрипт видит новый путь и добавляет его в индекс. Изменение и удаление файлов определяется так же. Содержимое сравнивается по sha256, а не по дате изменения, поэтому git checkout и копирование файлов не вызывают лишней переиндексации.

Источник можно заменить без изменения кода: достаточно смонтировать нужную папку в knowledge_base/ или задать переменную KNOWLEDGE_BASE_DIR.

## Как работает src/update_index.py

1. Берет блокировку faiss_index/.update.lock, чтобы cron и ручной запуск не работали одновременно.
2. Сканирует источник и считает sha256 каждого файла.
3. Читает манифест faiss_index/manifest.json (путь файла, sha256, число чанков) и сравнивает с текущим состоянием: новые, измененные, удаленные, без изменений.
4. Читает только новые и измененные файлы, проверяет их правилами src/injection_guard.py из задания 5 (по умолчанию предупреждение в лог, с флагом --quarantine файл не индексируется).
5. Режет на чанки с теми же параметрами, что build_index.py: RecursiveCharacterTextSplitter, 1200 символов, перекрытие 100, те же metadata (source, title, chunk_id, chunk_index).
6. Считает эмбеддинги моделью из config.EMBEDDING_MODEL_NAME (intfloat/multilingual-e5-small). Модель загружается только если есть что векторизовать, поэтому запуск без изменений быстрый и не требует сети.
7. Удаляет из FAISS чанки измененных и удаленных файлов, добавляет новые.
8. Сохраняет индекс через временную папку и замену файлов (сначала index.pkl, затем index.faiss), после этого записывает манифест.
9. Пишет итог в логи и возвращает код выхода.

Диаграммы: docs/diagrams/task6_architecture.puml (архитектура и поток данных) и docs/diagrams/task6_update_flow.puml (алгоритм запуска), рядом лежат готовые PNG.

## Режимы

| Режим | Когда | Что происходит |
| --- | --- | --- |
| incremental | есть изменения, манифест согласован с индексом | правятся только затронутые документы |
| noop | изменений нет | ничего не пересчитывается, индекс не перезаписывается |
| full | нет манифеста, сменились модель, backend или параметры чанков, индекс поврежден, число векторов не сходится с манифестом, флаг --full | индекс собирается заново из всех файлов |
| dry-run | флаг --dry-run | печатается план изменений, ничего не записывается |

Полная пересборка при смене параметров нужна, чтобы не смешивать в одном индексе векторы разных моделей или разных размеров чанка. Первый запуск на репозитории, где манифеста еще нет, тоже выполняется в режиме full и воспроизводит индекс из заданий 3-5 (33 документа, 33 чанка при размере чанка 1200).

## Защита от сбоев

- Пустой или недоступный источник (папка не смонтирована) не стирает индекс: запуск завершается ошибкой. Очистить индекс осознанно можно флагом --allow-empty.
- Файл, который не удалось прочитать, не ломает остальные: ошибка пишется в лог, остальные документы обновляются, статус запуска partial, код выхода 1. Если такой файл уже был в индексе, его прежние чанки остаются.
- Любая фатальная ошибка (нет сети для загрузки модели, нехватка места) происходит до записи индекса, поэтому предыдущая версия остается рабочей.
- Индекс и манифест записываются атомарной заменой файлов. Если процесс прервется между двумя записями, следующий запуск заметит расхождение числа векторов и манифеста и выполнит полную пересборку.
- Параллельные запуски исключены блокировкой, второй запуск завершается с кодом 3 и ничего не меняет.

## Логирование

Текстовый лог logs/update_index.log (ротация, 1 МБ, 5 файлов), время в UTC:

```
2026-10-02 06:00:03 UTC INFO update started, source=knowledge_base, index=faiss_index, model=intfloat/multilingual-e5-small, backend=huggingface
2026-10-02 06:00:03 UTC INFO files found: 34 (added 1, changed 0, removed 0, unchanged 33)
2026-10-02 06:00:03 UTC INFO   added: knowledge_base/34_kashrim.md
2026-10-02 06:00:05 UTC INFO chunks: +1, -0, total 34; index size 94.2 KiB; embeddings 0.31 s; duration 1.84 s
2026-10-02 06:00:05 UTC INFO index updated at 2026-10-02 06:00:05 UTC, 1 files added, 0 changed, 0 removed, 0 errors
```

Это пример формата. Реальные значения времени и размера зависят от машины, настоящий лог после проверочного запуска лежит в logs/update_index.log.

Машиночитаемый журнал logs/update_runs.jsonl содержит по одной записи на запуск: started_at, finished_at, duration_sec, status (ok, partial, error), mode, reason, files_added, files_changed, files_removed, files_unchanged, files_quarantined, chunks_added, chunks_removed, chunks_total, index_size_bytes, embed_time_sec, errors, warnings. Его удобно использовать в задании 7 для аналитики.

## Периодический запуск

Расписание: каждый день в 06:00.

Вариант 1, cron на хосте (Linux, macOS):

```bash
scripts/install_cron.sh              # установить на 06:00
scripts/install_cron.sh "30 5 * * *" # другое время
scripts/install_cron.sh --show       # проверить запись
scripts/install_cron.sh --remove     # удалить
```

Скрипт создает запись вида `0 6 * * * cd <проект> && <проект>/scripts/run_update.sh >> <проект>/logs/cron.log 2>&1`. Время берется по часовому поясу системы. Шаблон для ручной установки: deploy/crontab.

Вариант 2, планировщик в Docker: сервис updater в docker-compose.yml запускает cron внутри контейнера по расписанию из deploy/crontab (06:00 UTC), использует те же папки knowledge_base/, faiss_index/ и logs/ через volume. Переменная RUN_ON_START=true дополнительно делает обновление при старте контейнера.

```bash
docker compose up -d bot updater
docker compose logs -f updater
```

Вариант 3, Windows: планировщик заданий, команда `schtasks /Create /SC DAILY /ST 06:00 /TN QuantumForgeUpdate /TR "C:\путь\.venv\Scripts\python.exe C:\путь\src\update_index.py"`. Блокировка параллельных запусков на Windows отключена, поэтому для боевого использования рекомендуется Linux или Docker.

Что происходит при ошибке: scripts/run_update.sh повторяет запуск при коде выхода 1 до UPDATE_ATTEMPTS раз (по умолчанию 3) с паузой UPDATE_RETRY_DELAY_SEC секунд (по умолчанию 300). Код 3 (уже выполняется) не повторяется. После последней неудачной попытки в update_index.log добавляется запись об ошибке, индекс остается в прежнем рабочем состоянии, а в cron.log и update_runs.jsonl видна причина.

## Связь с остальными заданиями

- Задание 3: тот же формат индекса (FAISS IndexFlatL2, 384 измерения), те же параметры чанков и metadata. build_index.py остается способом первичной сборки, update_index.py его дополняет.
- Задание 4: src/rag_pipeline.py перечитывает индекс, если index.faiss изменился на диске (метод _reload_if_changed). Перезапуск бота после обновления не нужен.
- Задание 5: вредоносный документ 33_zlonamerennyy_dokument.md по-прежнему индексируется, как того требует демонстрация защиты, но update_index.py пишет по нему предупреждение. В боевом режиме можно включить карантин (QUARANTINE_INJECTIONS=true или флаг --quarantine), тогда такие файлы в индекс не попадают.
- Задание 7: пробелы в базе знаний создаются удалением файлов из knowledge_base/ и запуском update_index.py, удаленные чанки пропадают из индекса. Журнал update_runs.jsonl можно использовать как источник данных для анализа.

## Как проверить

Автотесты (офлайн, без модели и сети):

```bash
python -m unittest discover -s tests -v
```

Ручной сценарий на боевой модели:

```bash
python src/update_index.py --dry-run          # посмотреть план
python src/update_index.py                    # первый запуск, режим full
python src/update_index.py                    # повторный запуск, режим noop
cp examples/34_kashrim.md knowledge_base/     # новый документ
python src/update_index.py                    # режим incremental, +1 файл
python scripts/check_search.py "Как называется родная планета Тарвинов?"
python scripts/index_stats.py                 # индекс согласован с манифестом
```

## Ограничения

- Переименование файла выглядит как удаление и добавление, его чанки пересчитываются.
- Тестовый backend эмбеддингов (EMBEDDINGS_BACKEND=stub) предназначен только для автотестов и проверки без доступа к Hugging Face, на боевом индексе его использовать нельзя. Из-за хранения backend в манифесте переключение приведет к полной пересборке.
- Для базы в десятки тысяч документов (объем, заявленный в задании 1) FAISS IndexFlatL2 по-прежнему подходит, но первая полная пересборка займет заметное время, поэтому ее лучше выполнять вне рабочих часов.
