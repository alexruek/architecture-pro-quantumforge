# Задание 1. Исследование моделей и инфраструктуры

## Контекст задачи

QuantumForge Software - финско-эстонский разработчик платформы Digital Twin. База знаний включает около 18000 markdown-файлов, 3000 страниц Confluence и 250 PDF-спецификаций, прирост около 400 страниц в месяц. Около 20 процентов оборота компании приходится на консалтинг по интеграции с SCADA-системами клиентов, часть документации по этому направлению может содержать данные заказчиков и подпадает под требования конфиденциальности и GDPR как для европейской компании. Это влияет на выбор облачных сервисов для части контента.

## 1. Сравнение LLM-моделей

| Критерий | Локальные HuggingFace модели (Llama 3.1 8B, Mistral 7B) | OpenAI (gpt-4o-mini, gpt-4o) | YandexGPT |
| --- | --- | --- | --- |
| Качество ответов | Среднее, сильно зависит от качества промптов и найденного контекста | Высокое, стабильно следует инструкциям и формату ответа | Среднее, лучше работает с русскоязычными запросами |
| Скорость работы | На CPU медленно, 5-15 секунд на ответ, на GPU быстро | Быстро, 1-3 секунды на ответ | Быстро, 1-3 секунды на ответ |
| Инфраструктурные затраты | Нужен сервер с GPU для приемлемой скорости, разовые вложения в железо | Отсутствуют, только оплата по токенам | Отсутствуют, только оплата по токенам |
| Стоимость использования | Условно бесплатно после покупки железа, есть расходы на электричество и обслуживание | gpt-4o-mini - около 0.15 доллара за 1 млн входных токенов | Сопоставимо с OpenAI, тарификация в рублях |
| Удобство развертывания | Сложнее, нужно настраивать inference-сервер (vLLM, TGI) и следить за обновлениями | Просто, вызов API | Просто, вызов API |
| Работа с конфиденциальными данными | Полный контроль, данные не покидают периметр компании | Данные передаются провайдеру, нужен договор об обработке данных | Данные передаются провайдеру |

Вывод: для основного потока вопросов (документация, онбординг новых сотрудников, ответы поддержки) облачная модель выгоднее по совокупности скорости, качества и простоты поддержки. Для консалтингового направления, где документы могут содержать данные клиентов, целесообразно рассмотреть локальную модель или облачную с закрепленным договором о неиспользовании данных для обучения.

## 2. Сравнение моделей эмбеддингов

| Критерий | Sentence-Transformers, локально (bge-base-en-v1.5) | OpenAI Embeddings (text-embedding-3-small) |
| --- | --- | --- |
| Скорость создания индекса | На CPU для базы объемом около 15 млн токенов - несколько часов, на GPU - десятки минут | Зависит от лимитов API и размера батча, время сопоставимо за счет сетевых задержек |
| Качество поиска | Хорошее для технической документации, достаточно для задачи компании | Хорошее, стабильно высокие показатели на бенчмарке MTEB |
| Прямые денежные затраты | Бесплатно после расчета на своем сервере | Около 0.02 доллара за 1 млн токенов, для базы такого объема разовая индексация обходится в доли доллара, ежемесячный прирост - копейки (расчет в cost_calculator.py) |
| Зависимость от внешних сервисов | Нет, работает офлайн | Есть, нужен стабильный доступ к API |
| Конфиденциальность | Документы не покидают периметр компании | Текст документов отправляется во внешний сервис для расчета вектора |

Вывод: при таком объеме базы прямая денежная разница между вариантами незначительна для обоих случаев. Решающими критериями становятся конфиденциальность (актуально для консалтингового направления с клиентскими SCADA-данными) и независимость от внешнего API и его лимитов. По этой причине для проекта выбрана локальная модель эмбеддингов.

## 3. Сравнение векторных баз FAISS и ChromaDB

| Критерий | FAISS | ChromaDB |
| --- | --- | --- |
| Скорость поиска и индексации | Очень высокая, библиотека оптимизирована для больших объемов векторов | Высокая, но за счет дополнительного слоя абстракции немного медленнее на больших объемах |
| Сложность внедрения | Низкая, прямая работа с индексом через Python | Низкая, удобный клиент, метаданные хранятся вместе с векторами |
| Удобство в работе | Метаданные нужно хранить отдельно, например в JSON рядом с индексом | Фильтрация по метаданным встроена, удобнее для аналитики покрытия из задания 7 |
| Обновление индекса | Возможно добавлять и удалять записи, но требует ручной работы с id | Есть готовые методы add, update, delete по id |
| Инфраструктура | Не требует отдельного сервиса, легко упаковывается в Docker вместе с ботом | В embedded-режиме сопоставима с FAISS, при развертывании как отдельного сервиса нужен дополнительный контейнер |
| Стоимость владения | Бесплатная библиотека | Бесплатная библиотека |

Вывод: для MVP и учебной части проекта FAISS проще и быстрее в развертывании, особенно в связке с langchain и Docker Compose, как и указано в задании курса. ChromaDB стоит рассмотреть при масштабировании, когда нужно часто добавлять и удалять отдельные чанки без пересборки всего индекса (актуально для задания 6 про автообновление) и когда важна встроенная фильтрация по метаданным для аналитики (задание 7).

## 4. Рекомендуемая конфигурация сервера

Для MVP версии с облачной LLM:

- CPU: 4-8 vCPU
- RAM: 16-32 GB, с запасом под индекс FAISS в памяти при объеме 20000 и более документов
- GPU: не требуется
- Диск: SSD от 50 GB под индекс, логи и кеш модели эмбеддингов

Если в дальнейшем потребуется локальная LLM для консалтингового направления:

- CPU: 8-16 vCPU
- RAM: 64 GB
- GPU: одна карта уровня NVIDIA A10 с 24 GB видеопамяти для модели 7-8B параметров
- Диск: SSD от 200 GB

## 5. Итоговые варианты решения

### Вариант 1. Полностью облачный стек

LLM - OpenAI gpt-4o-mini, эмбеддинги - OpenAI text-embedding-3-small, векторная база - FAISS локально или управляемый сервис.

Плюсы: минимум инфраструктуры, быстрый старт проекта.
Минусы: консалтинговые данные клиентов уходят во внешний сервис, расходы на токены растут вместе с объемом базы и числом запросов.

### Вариант 2. Полностью локальный стек

LLM - Llama 3.1 8B через vLLM, эмбеддинги - bge-base-en-v1.5, векторная база - FAISS.

Плюсы: полный контроль над данными, нет зависимости от внешних API и их лимитов.
Минусы: нужен сервер с GPU, выше расходы на обслуживание, качество ответов ниже, чем у топовых облачных моделей.

### Вариант 3. Гибридный стек (рекомендуемый)

LLM - облачная модель (OpenAI gpt-4o-mini) для общего потока вопросов по документации и онбордингу, локальная модель эмбеддингов bge-base-en-v1.5, векторная база FAISS. Для консалтингового направления с клиентскими данными - отдельный контур с локальной LLM или с облачной моделью с закрепленным договором о неиспользовании данных.

Плюсы: баланс стоимости, качества и требований конфиденциальности, эмбеддинги считаются один раз локально и не тарифицируются заново при каждом обновлении базы.
Минусы: два контура сложнее поддерживать и тестировать, чем один.

### Вариант 4. Бюджетный локальный стек без GPU

LLM и эмбеддинги полностью на CPU, векторная база FAISS.

Плюсы: минимальные вложения в инфраструктуру.
Минусы: заметная задержка ответа, 10-20 секунд, не подходит для рабочего инструмента, годится только для проверки концепции.

### Рекомендация

Вариант 3, гибридный стек. Он закрывает требование конфиденциальности для консалтингового направления и при этом не требует избыточных вложений в GPU-сервер для основного потока вопросов, а локальные эмбеддинги снижают зависимость от внешнего API при регулярном обновлении базы.

Для учебной части проекта (7 спринт) реализация ведется на связке FAISS плюс Sentence-Transformers плюс один LLM-провайдер на выбор студента, но архитектура закладывается так, чтобы контур можно было разделить в дальнейшем при масштабировании на реальный проект.
