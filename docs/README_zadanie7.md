# Задание 7. Аналитика покрытия и качества базы знаний

Цель - понять, на какие вопросы бот не отвечает и почему: из-за того, что в базе нет нужного документа, или из-за того, что документ есть, но поиск его не находит. Для этого в базе созданы искусственные пробелы, каждое обращение к боту пишется в лог с полями для анализа, а качество проверяется автоматически на золотом наборе вопросов.

## Состав

## 1. Искусственные пробелы

Удалены три ключевые сущности, на которые опираются вопросы о сюжете:

| Документ | Сущность | Категория |
| --- | --- | --- |
| 01_ksarn_velgor.md | Ксарн Велгор | персонаж |
| 18_voyd_yadro.md | Войд-Ядро | технология |
| 21_sint_potok.md | Синт-Поток | технология |

Документы не стираются, а переносятся в kb_removed/ (python scripts/make_gaps.py apply), время операции записывается в kb_removed/_gaps.json. Индекс после этого обновляется скриптом задания 6: update_index.py видит три удаленных файла и точечно убирает их чанки из FAISS. Откат - python scripts/make_gaps.py restore и повторный запуск update_index.py.

## 2. Логирование запросов

Каждое обращение к боту (REST API, консоль, демо задания 5, прогон золотого набора) добавляет строку в logs/queries.jsonl. Поля, которые требует задание:

| Требование | Поле |
| --- | --- |
| текст запроса | query |
| timestamp | timestamp (UTC, ISO 8601) |
| были ли найдены чанки | chunks_found, relevant_chunks, retrieved_count |
| длина ответа | answer_length |
| флаг успешного ответа | success, outcome |
| найденные источники | sources |

Дополнительно: answer, status, top_score (лучшая оценка релевантности), candidates (все кандидаты поиска до отсечения порогом с оценками), latency_ms, interface, error, а у прогонов золотого набора - run_id, eval_tag, golden_id.

Флаг успешного ответа (src/quality.py). Ответ считается успешным, если бот вызвал LLM, получил непустой ответ длиннее 20 символов с источниками и итоговая часть ответа после "Ответ:" не содержит формулировок отказа ("не знаю", "нет информации", "не указан" и подобных). Итог обращения (outcome) различает пять случаев: answered, soft_refusal (LLM вызвана, но ответила "не знаю"), refused (релевантных чанков нет, LLM не вызывалась), blocked (сработала защита задания 5), error.

Записи заданий 4-5 в старом формате остаются в логе, аналитика вычисляет для них outcome по статусу и тексту ответа.

## 3. Золотой набор

golden_questions.txt, 13 вопросов, формат строки: id, тип, вопрос, ожидаемый ответ, ключевые слова, ожидаемый источник.

| Тип | Вопросы | Ожидание |
| --- | --- | --- |
| known | G01-G08: Дэйн Кориэл, Директива 66, Битва при Йовене, Хоррак, Странник Тысячелетия, Мастер Кадан Ирис, Крионис, Приверженцы Тени | ответ по документу |
| removed | G09-G11: Ксарн Велгор, Войд-Ядро, Синт-Поток | до удаления - ответ, после удаления - отказ |
| absent | G12 (учитель Мастера Кадана Ириса, в документе этого нет), G13 (цена подписки на Digital Twin, вне предметной области) | отказ |

Вопросы покрывают все категории базы: персонажи, планеты, технологии, организации, события. G12 проверяет самый неприятный случай: документ о сущности найдется, и модель может додумать ответ, которого в тексте нет.

## 4. Автоматическое тестирование

src/evaluate.py задает вопросы по очереди, пишет каждый ответ в logs/queries.jsonl, результаты оценки - в logs/eval_results.jsonl, отчет прогона - в docs/task7_eval_<метка>.md. Метка выбирается автоматически: baseline, если все документы на месте, gaps, если пробелы применены.

Ожидаемое поведение для вопросов removed вычисляется по состоянию базы, поэтому один и тот же набор корректно проверяет индекс до и после удаления документов.

Что оценивается по каждому вопросу:

- ответ найден: да/нет;
- полнота: доля ключевых слов из набора в ответе (0..1), слово засчитывается по основе, поэтому падежные формы тоже подходят;
- источник найден: ожидаемый документ среди источников ответа;
- ранг и оценка ожидаемого документа среди кандидатов поиска, даже если он не прошел порог;
- вердикт.

| Вердикт | Значение | Прошел |
| --- | --- | --- |
| correct | ответ найден, источник верный, полнота не ниже 0.5 | да |
| correct_refusal | ожидался отказ, бот отказал | да |
| incomplete | источник верный, но полнота ниже 0.5 | нет |
| wrong_source | ответ дан по другому документу | нет |
| miss_threshold | ожидаемый документ был среди кандидатов, но отсечен порогом | нет |
| miss_retrieval | ожидаемого документа нет среди кандидатов | нет |
| soft_refusal_known | документ найден, но LLM ответила "не знаю" | нет |
| blocked_false_positive | защита задания 5 заблокировала обычный вопрос | нет |
| answered_on_gap | ответ на вопрос, данных для которого в базе нет | нет |
| error | сбой поиска или генерации | нет |

Разделение промахов на miss_threshold и miss_retrieval показывает, что чинить: порог или модель эмбеддингов.

Проверка обновленного индекса встроена в ежедневный запуск задания 6. Если в .env задано RUN_EVAL_AFTER_UPDATE=true, scripts/run_update.sh после успешного обновления запускает evaluate.py с порогом EVAL_MIN_PASS (по умолчанию 0.7). Результат пишется в logs/update_index.log, отчет - в logs/eval_last_report.md, при падении качества скрипт завершается с кодом 4, который видит cron и система мониторинга. Переменные прокинуты в сервис updater в docker-compose.yml.

## 5. Анализ логов

src/analyze_logs.py читает все обращения и прогоны и формирует docs/task7_log_analysis.md:

1. Итоги обращений по outcome и покрытие по категориям сущностей.
2. Темы, по которым бот не отвечает. Вопрос сопоставляется с сущностью базы по заголовку документа с учетом падежей. Для каждой темы указано, был ли документ в базе на момент запроса (по времени из kb_removed/_gaps.json), и причина: пробел покрытия, проблема поиска или вопрос вне базы.
3. Нерелевантные источники: ответы без документа темы среди источников или с лишними документами других сущностей.
4. Оценки релевантности и подбор порога: для каждого порога считается, сколько решений "отвечать или отказать" на уровне поиска были бы верными.
5. Сравнение прогонов baseline и gaps по каждому вопросу.
6. Аудит текстов базы (kb_audit.py).
7. Список выявленных пробелов с основаниями и рекомендации.

Блокировки защитой и прогон уровней защиты задания 5 из анализа покрытия исключены: это вопросы безопасности, а не полноты базы.

## 6. Диаграмма

docs/diagrams/task7_eval_sequence.puml (и PNG): прогон золотого набора, обработка одного вопроса в RagPipeline, запись лога, оценка, аналитика. Отмечены точки сбоя и реакция на них:

- индекса нет или он поврежден - прогон останавливается с кодом 2 и подсказкой пересобрать индекс;
- индекс пуст - прогон останавливается, иначе все ответы были бы отказами и отчет вводил бы в заблуждение;
- невалидный чанк (пустой текст, нет source) - не попадает в контекст, учитывается в invalid_chunks;
- сбой генерации (таймаут, нет сети, ошибка API) - бот возвращает status=error, ошибка пишется в лог, прогон продолжается со следующего вопроса.

## 7. Выводы

Полные цифры - в docs/task7_eval_baseline.md, docs/task7_eval_gaps.md и docs/task7_log_analysis.md.

Плохо покрытые темы:

- Ксарн Велгор, Войд-Ядро, Синт-Поток - пробелы покрытия. После удаления документов бот на эти вопросы честно отказывает, ни одна из сущностей не описана в других документах достаточно, чтобы ответить по ним. При этом связанные документы (Битва при Йовене, Союз Свободных Миров) описывают станцию и темного лорда без имен, поэтому даже частичный ответ по ним невозможен: перекрестные ссылки в базе сделаны описаниями, а не названиями.
- Ксарн Велгор и Войд-Ядро не находились и до удаления документов: в прогоне задания 5 (logs/demo_log.md) на полной базе бот отказал по обоим вопросам. Это проблема поиска, а не покрытия: all-MiniLM-L6-v2 обучена на английском, на коротких русских вопросах оценки получаются низкими и не проходят порог.
- Вопрос об учителе Мастера Кадана Ириса - пробел фактов внутри существующего документа.

Сколько пробелов выявлено: три искусственных пробела покрытия, один пробел факта в существующем документе, сущности, которые есть в базе, но не находятся поиском (по данным прогона), и дефекты текста в 9 документах. Итоговое число с расшифровкой - в разделе 8 отчета docs/task7_log_analysis.md.

Дефекты текстов базы, найденные аудитом (не зависят от модели):

- остатки исходных имен после замены терминов: "Люк" (02_deyn_koriel.md), "Лея" (03_princessa_mira_alten.md), "Хан" (04_reks_dorian.md), "Винду" (10_master_kadan_iris.md);
- смешение терминологии: в трех документах встречается "империя" вместо "Гегемония";
- слова, испорченные заменой "Хот" -> "Крионис" внутри слова "охотник" ("оКрионисник" в 04, 11, 24, "неоКрионисно" в 06) и формами "Сила" -> "Синт-Поток" ("Синт-Потокм" в 04, "Синт-Потокми" в 18). Документ 18 сейчас перенесен в kb_removed/, поэтому отчет аналитики считает дефекты по 9 оставшимся документам, но при возврате его тоже нужно исправить.

Такие дефекты ухудшают и поиск, и ответы: искаженное слово не совпадает ни с одним запросом, а остаток исходного имени связывает текст с известной модели вселенной.

## 8. Рекомендации по улучшению базы знаний

Для учебной базы:

1. Вернуть или переписать документы по удаленным сущностям, проверить, что золотые вопросы G09-G11 снова проходят.
2. Исправить тексты: заменить остатки исходных имен, починить испорченные слова, выровнять терминологию. В scripts/replace_terms.py замену делать только по границам слов, иначе короткие термины ("Хот") попадают внутрь других слов.
3. Дополнить документы фактами, о которых спрашивают (учитель Мастера Кадана Ириса), и добавить в документы названия связанных сущностей, а не только описания: "атакует Войд-Ядро", а не "атакует первую боевую станцию".

Для системы QuantumForge:

1. Перейти на многоязычную модель эмбеддингов (multilingual-e5-base или bge-m3) и подобрать порог релевантности заново по таблице раздела 5 отчета аналитики. Порог зависит от модели, переносить его нельзя.
2. Включить RUN_EVAL_AFTER_UPDATE=true: каждое ночное обновление индекса проверяется золотым набором, падение качества видно утром, а не по жалобам сотрудников.
3. Раз в неделю запускать analyze_logs.py по живым логам и превращать темы без ответа в задачи владельцам разделов документации. Каждый вопрос без ответа, на который ответ должен быть, добавлять в золотой набор.
4. Назначить владельца каждому разделу базы (проблема "у страниц нет владельца" из описания компании) и считать по логам долю успешных ответов по разделам.
5. Добавить аудит текстов (kb_audit.py) в проверку при загрузке документов: дубли, устаревшие термины и битые замены ловятся до индексации.
6. Для оценки полноты ответов на большом наборе дополнить проверку по ключевым словам оценкой LLM-судьей (faithfulness, answer relevance), как в RAGAS, и сверять ее с ручной разметкой на выборке.

## Запуск

```bash
python src/evaluate.py --tag baseline        # прогон на полной базе
python scripts/make_gaps.py apply            # создать пробелы
python src/update_index.py                   # обновить индекс (задание 6)
python src/evaluate.py --tag gaps            # прогон с пробелами
python src/analyze_logs.py                   # отчет аналитики
python -m unittest discover -s tests -v      # автотесты
```
