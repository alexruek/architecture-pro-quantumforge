# Задание 7. Аналитика покрытия и качества базы знаний

Цель - понять, на какие вопросы бот не отвечает и почему: из-за того, что в базе нет нужного документа, или из-за того, что документ есть, но поиск его не находит. Для этого в базе созданы искусственные пробелы, каждое обращение к боту пишется в лог с полями для анализа, а качество проверяется автоматически на золотом наборе вопросов.

## Состав

| Файл | Назначение |

## 1. Искусственные пробелы

Удалены три ключевые сущности, на которые опираются вопросы о сюжете. Выбраны сущности, которые в остальных документах упоминаются только описательно, без названия, поэтому после удаления документа сведений о них в базе не остается:

| Документ | Сущность | Категория |
| --- | --- | --- |
| 01_ksarn_velgor.md | Ксарн Велгор | персонаж |
| 18_voyd_yadro.md | Войд-Ядро | технология |
| 17_asterra.md | Астерра | планета |

Документы не стираются, а переносятся в kb_removed/ (python scripts/make_gaps.py apply), время операции записывается в kb_removed/_gaps.json. Индекс после этого обновляется скриптом задания 6: update_index.py видит три удаленных файла и точечно убирает их чанки из FAISS. Откат - python scripts/make_gaps.py restore и повторный запуск update_index.py.

## 2. Логирование запросов

Каждое обращение к боту (REST API, консоль, демо задания 5, прогон золотого набора) добавляет строку в logs/queries.jsonl. Поля, которые требует задание:

| Требование | Поле |
| --- | --- |
| текст запроса | query |
| timestamp | timestamp (UTC, ISO 8601) |
| были ли найдены чанки | chunks_found, relevant_chunks, retrieved_count |
| длина ответа | answer_length |
| флаг успешного ответа | success, outcome |
| найденные источники | sources |

Дополнительно: answer, status, top_score (лучшая оценка релевантности), candidates (все кандидаты поиска до отсечения порогом с оценками), latency_ms, interface, error, а у прогонов золотого набора - run_id, eval_tag, golden_id.

Флаг успешного ответа (src/quality.py). Ответ считается успешным, если бот вызвал LLM, получил непустой ответ длиннее 20 символов с источниками и итоговая часть ответа после "Ответ:" не содержит формулировок отказа ("не знаю", "нет информации", "не указан" и подобных). Итог обращения (outcome) различает пять случаев: answered, soft_refusal (LLM вызвана, но ответила "не знаю"), refused (релевантных чанков нет, LLM не вызывалась), blocked (сработала защита задания 5), error.

Записи заданий 4-5 в старом формате остаются в логе, аналитика вычисляет для них outcome по статусу и тексту ответа.

## 3. Золотой набор

golden_questions.txt, 13 вопросов, формат строки: id, тип, вопрос, ожидаемый ответ, ключевые слова, ожидаемый источник.

| Тип | Вопросы | Ожидание |
| --- | --- | --- |
| known | G01-G08: Дэйн Кориэл, Директива 66, Битва при Йовене, Хоррак, Странник Тысячелетия, Мастер Кадан Ирис, Крионис, Приверженцы Тени | ответ по документу |
| removed | G09-G11: Ксарн Велгор, Войд-Ядро, Астерра | до удаления - ответ, после удаления - отказ |
| absent | G12 (учитель Мастера Кадана Ириса, в документе этого нет), G13 (цена подписки на Digital Twin, вне предметной области) | отказ |

Вопросы покрывают все категории базы: персонажи, планеты, технологии, организации, события. G12 проверяет самый неприятный случай: документ о сущности найдется, и модель может додумать ответ, которого в тексте нет.

## 4. Автоматическое тестирование

src/evaluate.py задает вопросы по очереди, пишет каждый ответ в logs/queries.jsonl, результаты оценки - в logs/eval_results.jsonl, отчет прогона - в docs/task7_eval_<метка>.md. Метка выбирается автоматически: baseline, если все документы на месте, gaps, если пробелы применены. Прогон останавливается с кодом 2, если метка задана вручную и не соответствует состоянию базы или если индекс не обновлен после изменения базы (манифест индекса расходится со списком файлов).

Ожидаемое поведение для вопросов removed вычисляется по состоянию базы, поэтому один и тот же набор корректно проверяет индекс до и после удаления документов.

Что оценивается по каждому вопросу:

- ответ найден: да/нет;
- полнота: доля ключевых слов из набора в ответе (0..1), слово засчитывается по основе, поэтому падежные формы тоже подходят;
- источник найден: ожидаемый документ среди источников ответа;
- ранг и оценка ожидаемого документа среди кандидатов поиска, даже если он не прошел порог;
- вердикт.

| Вердикт | Значение | Прошел |
| --- | --- | --- |
| correct | ответ найден, источник верный, полнота не ниже 0.5 | да |
| correct_refusal | ожидался отказ, бот отказал | да |
| incomplete | источник верный, но полнота ниже 0.5 | нет |
| wrong_source | ответ дан по другому документу | нет |
| miss_threshold | ожидаемый документ был среди кандидатов, но отсечен порогом | нет |
| miss_retrieval | ожидаемого документа нет среди кандидатов | нет |
| soft_refusal_known | документ найден, но LLM ответила "не знаю" | нет |
| blocked_false_positive | защита задания 5 заблокировала обычный вопрос | нет |
| answered_on_gap | ответ на вопрос, данных для которого в базе нет | нет |
| error | сбой поиска или генерации | нет |

Разделение промахов на miss_threshold и miss_retrieval показывает, что чинить: порог или модель эмбеддингов.

Проверка обновленного индекса встроена в ежедневный запуск задания 6. Если в .env задано RUN_EVAL_AFTER_UPDATE=true, scripts/run_update.sh после успешного обновления запускает evaluate.py с порогом EVAL_MIN_PASS (по умолчанию 0.7). Результат пишется в logs/update_index.log, отчет - в logs/eval_last_report.md, при падении качества скрипт завершается с кодом 4, который видит cron и система мониторинга. Переменные прокинуты в сервис updater в docker-compose.yml.

## 5. Анализ логов

src/analyze_logs.py читает все обращения и прогоны и формирует docs/task7_log_analysis.md:

1. Итоги обращений по outcome и покрытие по категориям сущностей.
2. Темы, по которым бот не отвечает. Вопрос сопоставляется с сущностью базы по заголовку документа с учетом падежей. Для каждой темы указано, был ли документ в базе на момент запроса (по времени из kb_removed/_gaps.json), и причина: пробел покрытия, проблема поиска или вопрос вне базы.
3. Нерелевантные источники: ответы без документа темы среди источников или с лишними документами других сущностей.
4. Оценки релевантности и подбор порога: для каждого порога считается, сколько решений "отвечать или отказать" на уровне поиска были бы верными.
5. Сравнение прогонов baseline и gaps по каждому вопросу.
6. Аудит текстов базы (kb_audit.py).
7. Список выявленных пробелов с основаниями и рекомендации.

Блокировки защитой и прогон уровней защиты задания 5 из анализа покрытия исключены: это вопросы безопасности, а не полноты базы.

## 6. Диаграмма

docs/diagrams/task7_eval_sequence.puml (и PNG): прогон золотого набора, обработка одного вопроса в RagPipeline, запись лога, оценка, аналитика. Отмечены точки сбоя и реакция на них:

- индекса нет или он поврежден - прогон останавливается с кодом 2 и подсказкой пересобрать индекс;
- индекс пуст - прогон останавливается, иначе все ответы были бы отказами и отчет вводил бы в заблуждение;
- невалидный чанк (пустой текст, нет source) - не попадает в контекст, учитывается в invalid_chunks;
- сбой генерации (таймаут, нет сети, ошибка API) - бот возвращает status=error, ошибка пишется в лог, прогон продолжается со следующего вопроса.

## 7. Выводы

Параметры прогонов: эмбеддинги intfloat/multilingual-e5-small, LLM gpt-4o-mini, TOP_K 4, порог релевантности 0.76. Полные таблицы - в docs/task7_eval_baseline.md, docs/task7_eval_gaps.md и docs/task7_log_analysis.md.

Результаты золотого набора:

| Прогон | Документов в индексе | Прошли проверку | Ответ найден, где ожидался | Корректных отказов |
| --- | --- | --- | --- | --- |
| baseline (полная база) | 34 | 13 из 13 (100%) | 11 из 11 | 2 из 2 |
| gaps (после удаления трех документов) | 31 | 12 из 13 (92%) | 8 из 8 | 4 из 5 |

На полной базе ожидаемый документ во всех 11 вопросах стоит первым в выдаче, средняя полнота ответов по ключевым словам 0.94.

Плохо покрытые темы:

- Ксарн Велгор, Войд-Ядро, Астерра - пробелы покрытия. На полной базе бот отвечает на все три вопроса (G09-G11, вердикт correct), после удаления документов отказывает без вызова LLM (correct_refusal). Аудит подтверждает, что ни одна из трех сущностей не названа по имени в оставшихся документах, поэтому ответить по соседним документам нельзя. Лучшая оценка кандидатов по этим вопросам падает с 0.81-0.84 до 0.71-0.73 и не проходит порог.
- Учитель Мастера Кадана Ириса (G12) - пробел факта внутри существующего документа. Документ о мастере находится с оценкой 0.814 и проходит порог, но сведений об учителе в нем нет.
- Вопросы вне предметной области (погода, цена подписки) - 8 обращений в логе, все получили отказ. Пробелом базы это не считается.

Сколько пробелов выявлено: 4. Три пробела покрытия (удаленные сущности) и один пробел факта. Расшифровка - в разделе 8 отчета docs/task7_log_analysis.md.

Единственный непройденный вопрос - G12 в прогоне gaps, вердикт answered_on_gap. По существу бот отказал и в этом прогоне: "В контексте нет упоминания о том, кто был учителем... Ответ: Неизвестно, кто был учителем Мастера Кадана Ириса". В прогоне baseline тот же отказ был сформулирован через "я не знаю" и засчитан верно. Это ограничение оценки, а не выдуманный ответ: правила в src/quality.py распознают отказ по списку фраз, и слова "неизвестно" в нем нет. Вывод для практики: проверка по ключевым фразам дает ложные срабатывания на перефразированных отказах, список фраз нужно пополнять по логам или дополнять оценкой LLM-судьей.

Нерелевантные источники. Найден один случай: на вопрос о цвете клинка Мастера Кадана Ириса (G06) кроме документа о мастере (0.874) порог прошел документ о плазменном клинке (0.767 при пороге 0.76). Ответ верный, второй источник лишний. В остальных ответах источник один и совпадает с ожидаемым.

Порог релевантности. Оценки ожидаемых документов лежат в диапазоне 0.80-0.87, лучшие оценки по вопросам вне базы и по удаленным сущностям - 0.66-0.73. Порог 0.76 разделяет эти группы с запасом около 0.03 в каждую сторону. Запас небольшой: у этой модели оценки сжаты в узкий диапазон, поэтому при росте базы порог нужно перепроверять на золотом наборе. По таблице раздела 5 отчета аналитики порог 0.8 уже отсекает два верных документа, а порог 0.7 пропускает кандидатов по удаленным сущностям.

Покрытие по логам. В анализ вошло 47 обращений из 57 (блокировки защитой исключены), содержательный ответ получен на 35 (74%). Без ответа остались только вопросы вне базы, вопросы по удаленным сущностям и вопрос об учителе. Вопросов, на которые документ есть, а бот не ответил, в логе нет.

Аудит текстов базы: остатков исходных терминов и испорченных замен не найдено. Замечания: один короткий документ (13_centralis.md, 58 слов), один документ без категории с признаками промпт-инъекции (33_zlonamerennyy_dokument.md, оставлен намеренно для задания 5), 21 документ ни разу не попал в источники ответов, потому что по ним никто не спрашивал.

Что показала аналитика на предыдущей версии базы и индекса и что по ней исправлено:

- поиск. Индекс был построен на англоязычной all-MiniLM-L6-v2, золотой набор проходил на 38-46%: документ по вопросу либо не попадал в выдачу, либо отсекался порогом. После перехода на многоязычную модель и подбора порога скриптом scripts/tune_threshold.py набор проходит на 100% на полной базе;
- тексты базы. Аудит находил дефекты в 10 документах: остатки исходных имен ("Люк", "Лея", "Хан", "Винду"), слова, испорченные заменой короткого термина внутри другого слова ("оКрионисник" из "охотник") и неверными окончаниями ("Синт-Потокм"). Скрипт replace_terms.py переписан на замену по границам слов с явным словарем падежных форм;
- защита. Один подозрительный чанк в выдаче блокировал ответ целиком. Теперь он исключается из контекста, а ответ строится по остальным.

## 8. Рекомендации по улучшению базы знаний

Для учебной базы:

1. Вернуть документы по удаленным сущностям (python scripts/make_gaps.py restore, затем python src/update_index.py) и проверить, что вопросы G09-G11 снова проходят.
2. Дополнить документ 10_master_kadan_iris.md сведениями об учителе: об этом факте спрашивают, а в тексте его нет.
3. Называть в документах связанные сущности по именам, а не описаниями: "атакует Войд-Ядро", а не "атакует первую боевую станцию". Тогда вопросы, связывающие две сущности, будут находить оба документа, а потеря одного документа не обнулит знание о сущности.
4. Расширить золотой набор: 21 документ не покрыт ни золотыми вопросами, ни обращениями из логов, качество ответов по ним не проверяется.
5. Расширить короткий документ 13_centralis.md.
6. Сократить шум в контексте: отсекать кандидатов, которые заметно отстают от лучшего по оценке, или добавить переранжирование. Это убирает лишние источники вроде случая с G06.

Для системы QuantumForge:

1. Подбирать порог релевантности заново после каждой смены модели эмбеддингов и перепроверять его при росте базы: диапазоны оценок у моделей разные, а запас между "своими" и "чужими" документами небольшой.
2. Включить RUN_EVAL_AFTER_UPDATE=true: каждое ночное обновление индекса проверяется золотым набором, падение качества видно утром, а не по жалобам сотрудников.
3. Раз в неделю запускать analyze_logs.py по живым логам и превращать темы без ответа в задачи владельцам разделов документации. Каждый вопрос без ответа, на который ответ должен быть, добавлять в золотой набор.
4. Назначить владельца каждому разделу базы (проблема "у страниц нет владельца" из описания компании) и считать по логам долю успешных ответов по разделам.
5. Добавить аудит текстов (kb_audit.py) в проверку при загрузке документов и включить карантин документов с признаками промпт-инъекции (QUARANTINE_INJECTIONS=true).
6. Дополнить проверку по ключевым словам оценкой LLM-судьей (faithfulness, answer relevance), как в RAGAS, и сверять ее с ручной разметкой на выборке. Случай с G12 показывает, что правила на фразах ошибаются на перефразированных ответах.

## Запуск

```bash
python src/evaluate.py --tag baseline        # прогон на полной базе
python scripts/make_gaps.py apply            # создать пробелы
python src/update_index.py                   # обновить индекс (задание 6)
python src/evaluate.py --tag gaps            # прогон с пробелами
python src/analyze_logs.py                   # отчет аналитики
python -m unittest discover -s tests -v      # автотесты
```
